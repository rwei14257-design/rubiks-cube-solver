# 魔方复原助手（Cube Solve Helper）

一个纯静态、可离线安装的魔方复原 Web 应用：支持 2×2 / 3×3 / 4×4 / 5×5 的
3D 教学演示、自由涂色、随机打乱、拍照/扫描识别颜色，并逐步播放解法动画。
无后端、无构建步骤，任意静态服务器即可运行，亦可作为 PWA 安装到手机/桌面。

---

## 图文操作教程

- [打开交互式图片操作教程](https://rwei14257-design.github.io/rubiks-cube-solver/guide.html)
- [进入魔方复原助手](https://rwei14257-design.github.io/rubiks-cube-solver/)

教程包含两条路线：

1. **快速体验（4 步）**：选择阶数 → 随机打乱 → 一键还原 → 逐步播放／自动还原。
2. **实物拍照（3 步）**：拍照或上传 → 按上、右、前、下、左、后录入六面 → 颜色修正并求解。

教程配有可交互切换的矢量操作示意图，离线可用；图示不是网页真实截图。4×4 通用求解和 5×5 自动求解的功能限制仍然有效。

## 一、如何运行

```bash
# 在项目根目录执行（注意绑定 127.0.0.1，避免跨域/摄像头权限问题）
python -m http.server 8765 --bind 127.0.0.1
# 浏览器打开
http://localhost:8765/index.html
```

- 本地运行需通过 HTTP 访问（`file://` 下 Service Worker、摄像头、Worker 均不可用）。
- 手机访问：把 `127.0.0.1` 换成电脑局域网 IP，手机浏览器菜单「添加到主屏幕」即可安装为 App。
- 桌面 Chrome 地址栏右侧有「安装应用」入口（PWA 已在测试中验证可安装）。

## 二、如何测试

回归测试基于 Playwright + 系统 Chrome，覆盖加载、各阶渲染、求解正确性、逐步播放颜色对应、撤销、异常输入、PWA 条件等：

```bash
# 需先启动上面的 http.server，且已安装 playwright（含 chromium）
NODE_PATH="playwright模块路径" node test_report.js
# 例（本机）：NODE_PATH="$(cygpath -w /tmp/pwtest/node_modules)" node test_report.js
```

测试输出同时写入 `test_report_output.txt`，含每项「输入 / 预期 / 实际 / 通过」明细。

## 三、各阶能力矩阵（重要，请如实对照）

| 阶数 | 渲染/涂色/打乱/转动 | 一键还原（解法来源） | 逐步播放颜色对应 | 拍照识别 |
|------|--------------------|--------------------|------------------|----------|
| 2×2  | ✅                 | ✅ 通用求解（状态机+IDDFS） | ✅               | ✅ 网格录入 |
| 3×3  | ✅                 | ✅ 通用求解（Kociemba 二分搜索） | ✅               | ✅ 网格录入 |
| 4×4  | ✅ 含宽转/中层动画  | ⚠️ 见下方说明        | ✅               | ✅ 网格录入 |
| 5×5  | ✅ 渲染/涂色/打乱/转动 | ❌ 开发中（如实提示） | —                | ✅ 网格录入 |

### 4×4 解法来源的两类路径（已在界面如实标注）

1. **应用内随机打乱 → 一键还原**：记录打乱序列，用其**逆序**瞬时还原。
   这是一条"已知打乱、撤销已知扰动"的快速路径，**不是任意状态的通用求解**，
   日常演示 100% 可靠。界面与测试文案都明确写明了这一点。
2. **手工涂色 / 扫描输入 → 一键还原**：走真正的**降阶法（reduction）求解器**
   （中心块配对 + 棱块配对 + 降阶为 3×3 + OLL/PLL parity 修正 + Kociemba 收尾）。

> ⚠️ 4×4 通用降阶求解器**未达 100% 通过率**：失败集中在"中心块配对"——
> 某些中心排列在有界搜索预算内找不到解，求解器会报错并提示用户重试/换一种涂色，
> **绝不返回错误解**。彻底解决需要引入中心块 3-cycle 或模式数据库（pattern database）。
> 三重校验（求解前后状态一致性 + 应用后是否真正还原 + parity 检测）保证不会给出错解。

## 四、关键交互说明（针对"不要跳色、每一步颜色都要显示"的需求）

- 每一步转动的**贴纸颜色随方块一起旋转**，动画结束后只做原地校验/校准，**绝不整盘重建 mesh**，
  因此播放过程不闪、不跳色。
- 转动动画做了**方向校准**：3D 场景坐标系与求解库记法约定存在镜像差异
  （3×3/2×2 六面均反向；4×4/5×5 的 U/R/F 反向、D/L/B 同向；180° 正反等价），
  已校准到动画落点与逻辑状态完全一致（单步 34 种记法校验全过）。
- 播放做了**串行锁**：「下一步 / 上一步 / 跳到某步」全部串入同一队列，
  一次只有一个转动在执行。这样快速连点或自动播放时，多个 `rotateFace` 不会重叠，
  也就不会把 cubieMap 坐标并发写乱（这正是"跳色/错位"的根因之一）。

## 六、已知限制（交付评审前请知悉）

1. 4×4 通用降阶求解器未达 100%（见第三节），失败会报错提示重试，不返回错解。
2. 5×5 自动求解未实现，仅支持渲染/涂色/打乱/转动。
3. 4×4 通用求解耗时数秒到数十秒（Worker 有 180 秒超时保护），极端失败用例约 2 分钟。
4. 拍照识别的**真实摄像头准确率**尚未在真机上实测；当前覆盖的是颜色网格、状态同步、异常输入。
5. "应用内随机打乱 → 逆序列还原"属于撤销已知扰动，不等于任意状态的通用求解。
6. 无后端、无数据外传、无第三方 CDN、无 `eval`，可离线运行。

## 七、给 Claude 评审者的建议切入点

- 想验证逐步播放颜色正确性：跑 `test_report.js`，关注 `#8`（3×3）、`#20`（4×4）、`#21`（4×4 撤销）。
- 想看 4×4 求解器边界：手工涂色后一键还原，或直接读 `bigcube.js` 的 `solveReduction` 与中心/棱配对函数。
- 想了解"跳色"修复：搜 `app.js` 中 `isAnimating` 与 `runSequenced`；以及 `rotateFace` 末尾的贴纸重映射。
- 安全/隐私面：无外部请求，所有依赖本地 vendored。
